SECTION 1 — EXECUTIVE SUMMARY
================================================================================

AetherScribe Lab is a research platform that generates multi-agent narrative
stories under explicit quantum policy control. Unlike conventional LLM
storytellers that choose plot events inside the language model, AetherScribe
separates decision-making from prose generation:

  • A Variational Quantum Circuit (VQC) built with PennyLane computes a
    probability distribution over joint character actions at each scene.
  • One joint action is sampled from that distribution and locked.
  • Google Gemini (when configured) renders scene prose that must respect the
    locked actions, then scores narrative coherence.
  • An explainability layer and dedicated UI panel document the measured path,
    alternate branches, posteriors, trait influence, and counterfactual reasons.

The deliverables for each run are:

  1. A full manuscript (6–12 scenes, configurable)
  2. Per-scene quantum decision cards with metrics and why-not analysis
  3. A research dashboard of Plotly charts (tension, coherence, entropy, etc.)
  4. Structured episode logs suitable for audit, export, and publication

Target users: researchers in quantum ML, explainable AI, interactive narrative,
and creative systems; developers evaluating hybrid quantum-classical RL; and
demonstrators who need transparent multi-agent story generation.

SECTION 2 — PROBLEM STATEMENT AND DESIGN GOALS
================================================================================

2.1 PROBLEM
--------------------------------------------------------------------------------
Generative story systems often produce fluent text while hiding the reasoning
behind plot choices. Stakeholders cannot easily answer:

  • Why did the protagonist take this action and not another?
  • Which character's traits drove the outcome?
  • What alternate paths were considered?
  • Can the same premise be reproduced with traceable decisions?

2.2 DESIGN GOALS
--------------------------------------------------------------------------------

  GOAL                    IMPLEMENTATION
  ----------------------  ---------------------------------------------------
  Transparency            Log probs, action_idx, rejections before rendering
  Narrative integrity     LLM constrained to quantum-resolved joint actions
  Reproducibility         Episode logs store weights, state, diagnostics
  Human-readable XAI      ExplanationEngine + ui/decisions.py + quantum_panel
  Character identity      Director brief names propagate to prose and charts
  Research presentation   Manuscript tab, Dashboard tab, export helpers

2.3 NON-GOALS (CURRENT VERSION)
--------------------------------------------------------------------------------
  • Not a general-purpose chatbot or unconstrained creative writing tool
  • Not a production game engine (no real-time player input loop)
  • Not guaranteed deterministic stories (default policy uses stochastic sampling)
  • Not multi-user cloud deployment (local Streamlit session model)

SECTION 3 — TRIAD OF AUTHORITY ARCHITECTURE
================================================================================

AetherScribe enforces role separation across three authorities:

3.1 DECISION AUTHORITY — QUANTUM RL
--------------------------------------------------------------------------------
  Components : QuantumPolicy, QuantumActionSpace, EpisodeRunner (sample step)
  Library    : PennyLane (default.mixed device, 4 qubits)
  Input      : Encoded narrative state vector + combined trait vector
  Output     : Action probabilities, entropy, risk, attribution, sensitivity
  Rule       : Branch selection occurs BEFORE any scene text is generated

3.2 RENDERING AUTHORITY — LLM SCREENWRITER
--------------------------------------------------------------------------------
  Component  : StoryRenderer (llm/story_renderer.py)
  API        : Google Gemini (gemini-2.5-flash primary, gemini-2.0-flash fallback)
  Input      : Locked joint action, rationale, prior summary, director brief
  Output     : Scene prose (target 5–8 sentences, 180+ words), summary, coherence
  Rule       : Must render the specified actions; cannot override quantum branch

3.3 EXPLAINABILITY AUTHORITY — INTERPRETATION
--------------------------------------------------------------------------------
  Components : ExplanationEngine, ui/decisions.py, ui/quantum_panel.py
  Input      : VQC diagnostics, rejections, attribution, agent traits, name_map
  Output     : Policy rationale, alternate paths, influence bars, narrative trace
  Rule       : Counterfactual text must be grounded in logged posteriors; UI
               distinguishes selected branch P from peak branch P under sampling

SECTION 5 — QUANTUM REINFORCEMENT LEARNING CORE
================================================================================

5.1 QUANTUMPOLICY CLASS
--------------------------------------------------------------------------------
  File : quantum_policy/quantum_policy.py

  Device     : qml.device("default.mixed", wires=n_qubits)  [default n_qubits=4]
  Weights    : Random uniform in [0, π], updated after each scene
  Circuit layers per qubit wire i:
    1. RY(state_vec[i])           — narrative state encoding
    2. RY(trait_vec[i] * π)       — character trait biasing
    3. RZ(weights[i])             — variational trainable layer
  Measurement: qml.probs(wires=range(n_qubits)) → normalized probability vector

5.2 ACTION PROBABILITY MAPPING
--------------------------------------------------------------------------------
  Raw circuit outputs 2^n = 16 basis probabilities for n=4.
  QuantumActionSpace defines num_actions = 16 joint actions.
  get_action_probs() truncates to num_actions and renormalizes.

5.3 STEP DIAGNOSTICS (compute_step_diagnostics)
--------------------------------------------------------------------------------
  Returns dict:
    action_probs   — normalized over joint action indices
    entropy        — Shannon entropy of full_probs (bits)
    risk           — clip(0.6 * entropy/n_qubits + 0.4 * tension, 0, 1)
    attribution    — Protagonist / Antagonist / Ally influence shares
    sensitivity    — feature perturbation scores (when full_explain=True)

5.4 INFLUENCE ATTRIBUTION
--------------------------------------------------------------------------------
  When full_explain=True: perturbation-based attribution via get_influence_attribution
  Fast path: normalize first three trait channels to protagonist/antagonist/ally

5.5 POLICY UPDATE (REINFORCE-style)
--------------------------------------------------------------------------------
  Simplified update after each scene:
    weights[i] += lr * reward * (action_index / (n_qubits + 1))
  Weights clipped to [0, 2π]
  Reward = env_reward * coherence_score (composite)

5.6 STATE ENCODING
--------------------------------------------------------------------------------
  File : environment/state_representation.py
  Method : StateRepresentation.encode(phase, tension, genre, step)

  Four features mapped to qubit rotation inputs:
    Tension   — float in [0, 1]
    Phase     — intro → 0.0, rising → 0.5, climax → 1.0
    Progress  — step / max_steps
    Genre     — numeric encoding from genre string

SECTION 6 — MULTI-AGENT ACTION SPACE
================================================================================

6.1 QUANTUMACTIONSPACE
--------------------------------------------------------------------------------
  File : quantum_policy/quantum_action_space.py
  Agents : ProtagonistAgent, AntagonistAgent, AllyAgent (agents/)

  num_actions = 16 (matches 2^4 qubit measurement outcomes)

  Each joint action is a dict:
    {"Protagonist": "<action>", "Antagonist": "<action>", "Ally": "<action>"}

  get_joint_action(index) returns joint_actions[index % 16]

6.2 ACTION REGISTRY
--------------------------------------------------------------------------------
  File : quantum_policy/action_registry.py
  Function : joint_action_to_env(joint_action)
  Maps display-style action strings to environment snake_case keys used in
  StoryEnvironment.ACTION_IMPACT (e.g. tension deltas, relationship updates).

6.3 CHARACTER TRAITS (SUMMARY)
--------------------------------------------------------------------------------
  Protagonist : aggression, curiosity, resilience, empathy (typical)
  Antagonist  : hostility, strategic_depth, manipulation, ruthlessness
  Ally        : loyalty, supportiveness, resourcefulness, sacrifice

  EpisodeRunner._get_combined_trait_vec() aggregates pairs into 4-channel vector
  fed to the VQC as trait_vec.

  See SECTION 26 for the complete list of 16 joint action combinations.

SECTION 7 — NARRATIVE ENVIRONMENT (STORYENVIRONMENT)
================================================================================

7.1 OVERVIEW
--------------------------------------------------------------------------------
  File : environment/story_environment.py

  Manages narrative physics: tension, phase, relationships, step counter.
  Genre-specific tension multipliers from environment/genre_dynamics.py.

7.2 STATE OBJECT
--------------------------------------------------------------------------------
  {
    "genre": str,
    "phase": "intro" | "rising" | "climax",
    "tension": float [0, 1],
    "step": int,
    "relationships": {
      "protagonist_ally": {"trust", "enmity"},
      "protagonist_antagonist": {"trust", "enmity"},
      "ally_antagonist": {"trust", "enmity"}
    },
    "director_brief": dict
  }

7.3 PHASE EVOLUTION
--------------------------------------------------------------------------------
  tension > 0.75  → climax  (phase_index = 2)
  tension > 0.45  → rising  (phase_index = 1)
  else            → intro   (phase_index = 0)

7.4 RELATIONSHIP DYNAMICS
--------------------------------------------------------------------------------
  Trust/enmity updated from joint env actions (_update_relationships).
  Examples:
    Ally provide_critical_intelligence → +trust P–L
    Ally sacrifice_personal_safety     → +0.2 trust P–L
    Protagonist confront / Antagonist strike → +enmity P–A

7.5 REWARD (ENVIRONMENT)
--------------------------------------------------------------------------------
  composite_reward =
    r_tension (current tension)
    + r_progress (step/max_steps * 0.5)
    + r_stability (0.2)
    + r_synergy (protagonist_ally trust * 0.3)

  EpisodeRunner multiplies by LLM coherence for policy learning signal.

7.6 TERMINATION
--------------------------------------------------------------------------------
  done = True when current_step >= max_steps (6–12 in UI, default 8)

SECTION 8 — EPISODE ORCHESTRATION (EPISODERUNNER)
================================================================================

8.1 CLASS AND DEPENDENCIES
--------------------------------------------------------------------------------
  File : evaluation/episode_runner.py

  Constructor(env, policy, action_space, explainer, renderer)

8.2 MAIN LOOP (per scene)
--------------------------------------------------------------------------------
  1. Encode state → state_vec
  2. policy.compute_step_diagnostics(...) → probs, entropy, risk, attribution
  3. SAMPLE: action_idx = np.random.choice(len(probs), p=probs)
  4. joint_action = action_space.get_joint_action(action_idx)
  5. Build rejection_data for all i != action_idx with template reasons:
       prob < 0.05        → "Low posterior mass under current quantum state."
       prob < 0.3*max     → "Trait-state interference suppressed this branch."
       prob < 0.7*max     → "Character-trait misalignment with narrative phase."
       else               → "Strong alternative; dominated by marginal utility gap."
  6. Sort rejections by prob descending
  7. env.step(env_action) → next_state, env_reward, done
  8. ExplanationEngine.generate_explanation(...) → rationale string
  9. Optional StoryRenderer.analyze_rejections(...) if render_depth == "full"
  10. StoryRenderer.render_scene(...) → story, summary, coherence
  11. composite_reward = env_reward * coherence; policy.update(...)
  12. Append log_entry to episode_log

8.3 RETURN PAYLOAD
--------------------------------------------------------------------------------
  {
    "id": UUID string,
    "scenes": [ log_entry, ... ],
    "total_reward": float,
    "mode": str (e.g. "Long Story"),
    "render_depth": "full" | "standard" | "fast",
    "traits": list,
    "characters": dict from director_brief
  }

8.4 CALLBACK
--------------------------------------------------------------------------------
  on_step(log_entry, current, total) — used by app.py for progress bar

SECTION 10 — QUANTUM DECISION UI PANEL (v6.0)
================================================================================

10.1 LOCATION IN APP
--------------------------------------------------------------------------------
  Manuscript tab → Scenes & quantum trace → expand scene
  Renderer : ui/quantum_panel.py :: render_quantum_explain_panel(rec)
  Styles   : ui/styles.py (.qx-* CSS classes)

10.2 PANEL SECTIONS
--------------------------------------------------------------------------------
  HEADER     : "Quantum decision · Scene N of M"
  LEGEND     : Explains posteriors and stochastic sampling vs peak branch
  METRICS    : Selected branch P | Peak branch P | Entropy | Risk | Margin ΔP |
               Coherence
  NOTE       : Purple callout when selected posterior < peak posterior
  CHOSEN PATH: Table of character name → readable action
  RATIONALE  : Distilled measurement, driver, disposition, arc lines
  INFLUENCE  : Horizontal bar chart (normalized attribution %)
  ALTERNATES : Up to 3 cards — actions, posterior, full why-not paragraph
  TRACE      : Italic narrative trace sentence

10.3 METRIC DEFINITIONS (UI)
--------------------------------------------------------------------------------
  Selected branch P : probs[action_idx] — the sampled branch used in story
  Peak branch P     : max(probs) — highest mass in superposition
  Margin ΔP         : sorted(probs)[-1] - sorted(probs)[-2]
  Coherence         : LLM auditor score for scene (0–1)

10.4 SAMPLING NOTE TEXT (when applicable)
--------------------------------------------------------------------------------
  "The VQC distribution peaked at X% (<peak joint summary>), but this scene
   stochastically measured the selected branch at Y%."

10.5 WHY-NOT PARAGRAPH STRUCTURE
--------------------------------------------------------------------------------
  If alternate posterior > selected posterior:
    Lead sentence explains stochastic sampling (not argmax).
  Then: alternate summary, measured summary, template/LLM reason.

SECTION 19 — STOCHASTIC MEASUREMENT AND POSTERIOR SEMANTICS
================================================================================

19.1 DEFAULT ACTION SELECTION
--------------------------------------------------------------------------------
  action_idx = int(np.random.choice(len(probs), p=probs))

  This is intentional exploration-style sampling from the VQC distribution.

19.2 INTERPRETING POSTERIORS IN THE UI
--------------------------------------------------------------------------------
  Selected branch P : probability mass on the branch that was sampled
  Peak branch P     : max probability among all 16 branches

  These often differ. Example: selected 13%, alternate 49% is VALID — the
  alternate had higher mass but was not the random draw for this scene.

19.3 UI MITIGATIONS FOR CONFUSION
--------------------------------------------------------------------------------
  • Dual metrics (Selected vs Peak)
  • Sampling note callout
  • Why-not text explains higher-posterior alternates not selected
  • README and this report document the behavior

19.4 DETERMINISTIC MODE (research option)
--------------------------------------------------------------------------------
  Replace sampling with: action_idx = int(np.argmax(probs))
  Document this choice in publications — removes stochastic exploration.

SECTION 25 — GLOSSARY
================================================================================

  Action space        Set of 16 joint multi-agent action combinations
  Attribution         Share of quantum influence attributed to each character role
  Coherence score     LLM-judged alignment of prose with locked actions [0,1]
  Composite reward    env_reward × coherence_score
  Counterfactual      Alternate branch not selected; "why not" analysis
  Director brief      User premise + character names + genre configuration
  Episode             Full story run from reset to max_steps
  Joint action        Simultaneous actions for Protagonist, Antagonist, Ally
  Log entry           One scene's complete diagnostic and story record
  Measurement         Collapse / sample of one joint action from probs
  Peak branch P       Maximum posterior among all joint actions
  Posterior           VQC probability mass on a joint action index
  Rejection data      Sorted list of non-selected branches with reasons
  Selected branch P   Posterior on the sampled action_idx used in the story
  Stochastic sampling np.random.choice(probs) default selection mode
  Superposition       Distribution over branches before scene measurement
  Trait biasing       RY rotations from character trait vector
  VQC                 Variational Quantum Circuit (PennyLane policy)

27.1 DATASET AND STORY ENVIRONMENT [ACTUAL CODEBASE + framing text]
--------------------------------------------------------------------------------

The framework is evaluated in a SYNTHETIC narrative environment, not a static
corpus of human-authored novels:

  • StoryEnvironment (environment/story_environment.py) simulates tension,
    narrative phase (intro / rising / climax), and pairwise relationships
    (trust, enmity) among protagonist, antagonist, and ally.

  • Genre-conditioned dynamics use GENRE_TENSION_MULTIPLIER
    (environment/genre_dynamics.py). The Streamlit UI exposes six genres:
    Thriller, Horror, Comedy, Romance, Drama, Fantasy.

  • Each "episode" is a user-defined director brief: premise text, character
    names, genre, language, and 6–12 scenes. This is best described as a
    multi-agent interaction benchmark under controlled narrative physics rather
    than a fixed downloadable dataset.

  • Prompt templates (llm/prompt_templates.py) encode scene length, premise lock,
    and quantum-action constraints for the LLM renderer.

Suggested paper wording (adapt):

  "We evaluated the framework across multiple synthetic narrative regimes
   (fantasy, thriller, mystery-style conflict, drama) using a shared environment
   with dynamic tension, phase transitions, and evolving inter-character
   relationships. Each run used custom premises and joint-action branching from
   a 16-branch quantum policy space."

27.2 LLM CONFIGURATION [ACTUAL CODEBASE]
--------------------------------------------------------------------------------

The narrative engine is Google Gemini (google-generativeai), not LLaMA / GPT-4
as the primary path in this repository.

  Parameter              Typical / default in code

27.3 QUANTUM FRAMEWORK DETAILS [ACTUAL CODEBASE]
--------------------------------------------------------------------------------

  Parameter              Value (this repository)
  ---------------------  --------------------------------------------------
  Library                PennyLane
  Backend / simulator    default.mixed (mixed-state simulation)
  Qubits                 4 (QuantumPolicy.__init__(n_qubits=4))
  Circuit depth          3 effective layers per wire: RY(state) + RY(traits*π)
                         + RZ(trainable weights)
  Encoding               Angle-style RY on normalized state_vec[0..3]
  Trait biasing          RY(trait_vec[i]*π) on wire i
  Variational gates      RZ(weights[i]), weights ∈ [0, 2π] after clip
  Entanglement           No explicit CNOT layer in the current circuit — be
                         honest in the paper: this is a product-state style
                         VQC with independent wires unless you extend it.
  Measurement            qml.probs on all wires → 16 outcomes mapped to
                         num_actions = 16 joint actions
  Action selection       Stochastic: np.random.choice(len(probs), p=probs)

If your paper claims "deeper" entanglement, you must first implement it in
quantum_policy.py and update this table.

27.4 TRAINING / LEARNING CONFIGURATION [ACTUAL CODEBASE — not PPO/Adam]
--------------------------------------------------------------------------------

The current policy update is a lightweight online rule, not Adam + PPO.

  Parameter              Value / behavior
  ---------------------  --------------------------------------------------
  RL paradigm            Online scene-wise update (REINFORCE-style heuristic)
  Optimizer              None (no Adam); weights += lr * reward * scaling
  Learning rate (lr)     0.01 default in app.py → QuantumPolicy.update(..., lr)
  Episodes / epochs      Not batch-trained: one trajectory per "Generate";
                         weights optionally persist in Streamlit session_state
  Batch size             N/A (sequential scenes)
  Reward                 composite_reward = env_reward * coherence_score
  Exploration (eps)      0.01 passed to compute_step_diagnostics (diagnostics)

If you migrate to PPO / Adam / batched training, replace this subsection with
your new optimizer table — reviewers will ask for consistency with code.

SECTION 33 — FAILURE CASE ANALYSIS (add before Conclusion)
================================================================================

Reviewers respect honest failure analysis. Known or plausible failure modes:

  • API / token limits: empty or truncated scenes if max_output_tokens too low
    or rate limits hit (mitigated by GEMINI_MIN_OUTPUT_TOKENS and retries).

  • High-entropy episodes: semantically weak transitions when many branches
    carry similar mass and sampling jumps frequently.

  • Coherence auditor noise: borderline scores when premise is underspecified.

  • Name drift: rare role-label leakage if prompts are weakened (mitigated by
    name_map and post-checks where implemented).

  • Simulator-only quantum: findings may not transfer to noisy QPUs without
    hardware validation.

  • Stochastic measurement confusion: readers misread posteriors unless UI
    legend is present (addressed in v6.0 panel).

Document 1–2 concrete failure episodes from your logs with redacted text.

SECTION 34 — COMPLEXITY AND SCALABILITY ANALYSIS (add inside Methodology)
================================================================================

Order-of-growth sketch (classical simulation of VQC):

  Module                    Complexity notes
  ------------------------  --------------------------------------------------
  State encoding            O(d) for d=4 features
  Single VQC forward        O(n_qubits * depth); here n=4, depth constant
  Sensitivity (full_explain) O(d * forward) finite-difference style
  Episode length            O(T) scenes, T ≤ 12 typical
  LLM cost                  Dominates wall-clock: O(T) * (scene + summary +
                            coherence + optional rejections)
  Joint action space        Fixed |A| = 16 today; scaling to |A| product of
                            per-role catalogs grows multiplicatively

Inference cost: dominated by Gemini calls per scene (full render_depth incurs
multiple calls). Quantum simulation cost is comparatively small on CPU.
